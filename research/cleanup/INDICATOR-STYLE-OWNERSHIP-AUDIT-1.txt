A. EXECUTIVE VERDICT
--------------------

STYLE_AUDIT_GREEN_FRONTEND_ONLY

Wozduh factory colors live in ui_config/wozduh_layout.go RenderOpts (served
as /api/ui/manifest). Series are LWC LineSeries or one custom ChannelSeries.
Both accept ISeriesApi.applyOptions. Color override can stay entirely in the
frontend: sparse localStorage + applyOptions. No DAG, demand, history, or
Go market-engine change is required.

GPT corrections (this audit):

1. Do NOT add Go "editable capabilities" to the manifest for v1. Infer
   fields from kind + existing renderOptions keys (line.color vs channel
   upper/mid/lower/fill). Extra Go types would be a power plant.

2. Name the store `wozduh_color_prefs_v1`, not `indicator_style_prefs_v1`.
   Visibility is already Wozduh-scoped (`wozduh_visibility_prefs_live`).
   A generic indicator key pretends we have a second consumer. We do not.

3. ChannelSeries.defaultOptions AND ChannelRenderer.draw fallbacks are
   SECOND default layers. They must not become a competing SSOT. Mount
   always passes ui_config colors; draw fallbacks only fire if options
   omit a key.

4. ChartTheme.wozduhVolRsiEma12 / wozduhVolRsiEma5 are STALE (defined,
   never read). Do not wire overrides through ChartTheme.

5. Extreme bands (wozduh-extreme-bands.js) are pane chrome, not DDR
   Wozduh lines. Out of v1.

6. Visibility setSeriesVisible → onSubscriptionChange → wsSubscribeTf
   + optional /api/history fetch. Color apply MUST NOT call that path.
   That is the main architecture trap, not a renderer limitation.

7. Skip a standalone STYLE-CONTRACT-1 Go chapter. First product code can
   be FE resolver + tests that empty prefs leave factory appearance, then
   the Style tab. Collapse, do not scaffold unused types.

8. Settings menu has NO tabs today. Style is a new sibling section in
   the same floating menu, not a second floating menu and not a backend
   config panel.

9. Fill is a single rgba on the composed renderer (not a separate fill
   series). There is no fillLowerColor (that experiment was reverted).

C. FACTORY COLOR SSOT
---------------------

Yes: ui_config/wozduh_layout.go is the factory-style SSOT for Wozduh DDR
components. Served to the client as JSON via DashboardServer.handleUIManifest
← ui_config.BuildUIRegistry ← WozduhComponents().

This is a presentation manifest in Go, not market/indicator config.
Changing those strings does not replay WozduhNode.

Competing / stale layers (must not become SSOT):

- ChannelSeries.defaultOptions() duplicates blue/orange/fill rgba
- ChannelRenderer.draw uses opts.X || hardcoded fallback
- ChartTheme.wozduhVolRsiEma12='blue', wozduhVolRsiEma5='aqua' — unused
- Named CSS vs hex mix is factory-only; overrides should still be hex

Precedence to implement:

    user override (sparse)
        → ui_config factory (manifest renderOptions)
            → ChannelSeries.defaultOptions / draw fallback (safety net only)


D. RENDERER TYPE MAP
--------------------

1) LWC LineSeries
   create: chart.addLineSeries(seriesOpts) in DDRFactory._mountComponent
   initial: renderOptions.color (and lineWidth, lastValueVisible, …)
   mutate: series.applyOptions({ color })
   recreate: not required for color
   verdict: IN_PLACE_SAFE

2) ChannelSeries (web/channel-series.js) via chart.addCustomSeries
   one primitive draws fill + upper + mid + lower
   boundaries are NOT separate LineSeries
   fill is NOT a second series
   create: seriesOpts includes upperColor, midColor, lowerColor, fillColor
   mutate: ISeriesApi.applyOptions on the custom series; ChannelSeries.update
           stores options; draw() reads them
   recreate: not required if LWC forwards custom option keys (expected;
             STYLE-OVERRIDES-1 must prove with a test)
   verdict: IN_PLACE_SAFE (verify applyOptions custom keys)

3) Plot kind
   not mounted; no renderer; no Style row

Wozduh has no area/histogram components.


E. CHANNEL COLOR / FILL OWNERSHIP
---------------------------------

Both channel families: one composed ChannelSeries.

Stored in ui_config channel RenderOpts:
  upperColor, midColor, lowerColor, fillColor
  lineWidth, midLineWidth, upperLineStyle, lowerLineStyle  (not v1)

Applied at mount as custom series options. Runtime: applyOptions of those
keys independently — yes, if LWC merges options.

Fill format today: rgba(R,G,B,A) with factory alpha 0.12.
User v1 is COLOR only — do not add an opacity slider.
When the user picks a fill swatch, replace RGB and KEEP factory alpha
(0.12) unless they Reset fill (then full factory rgba returns).

No gradient on channels. Extreme-band gradients are unrelated chrome.

I. RESET / DEFAULT SEMANTICS
----------------------------

A. Reset one property: delete that field on the component object;
   delete the object if empty.
B. Reset one component: delete the component key.
C. Reset all Wozduh style: removeItem('wozduh_color_prefs_v1')
   (store is Wozduh-only in v1).

Then applyOptions with factory values from the current manifest
renderOptions (not from a snapshot taken at override time).

Never write factory colors into localStorage.
Never mutate ui_config from the client.


J. COMMAND FLOW
---------------

Style tab (command owner)
  → WozduhColorPrefs.set(id, field, hex) | delete
  → persist sparse JSON
  → EffectiveColor = override ?? manifest.renderOptions
  → DDRFactory.getSeries(id).applyOptions(patch)

No LWC → prefs echo.
No setSeriesVisible.
No onSubscriptionChange.

Chart is observation/paint only for color.


K. INITIAL LOAD / REHYDRATION
-----------------------------

Current mount: _mountComponent copies manifest renderOptions into
addLineSeries / addCustomSeries. _mountComponent no-ops if the id
already exists. TF switch hydrates data; it does not remount series
(boot.js calls buildPanes once in mountDDRLiveCutover).

Cleanest v1:

  create with factory renderOptions (unchanged appearance if no prefs)
  immediately applyEffectiveColors() from sparse store
  on Style change: applyOptions only
  on SettingsRenderer.refreshFromManifest (visibility remount of menu):
    re-apply colors if series still exist (idempotent)

If series are ever cleared/rebuilt, applyEffectiveColors after
buildPanes. Color store is independent of TF and of visibility.

Hidden series: applyOptions({color}) still valid; no data fetch.


L. LIVE APPLY PATH
------------------

Lines: IN_PLACE_SAFE — applyOptions({ color })
Channels: IN_PLACE_SAFE — applyOptions({ upperColor, midColor,
  lowerColor, fillColor })  [prove LWC custom option merge in tests]

No history reload if command path is applyOptions-only.

Architecture debt if Style reuses setSeriesVisible:
  would fire WS subscribe + possible /api/history + demand mask change.
  Do not reuse that function.


M. THEME INTERACTION
--------------------

Wozduh line/channel colors are fixed strings in the manifest, not CSS
variables and not ChartTheme lookups.

ChartTheme.applyCssVariables retints chrome (bg/grid/text), not Wozduh
series.

Dark/light switch today does not change Wozduh factory colors.
Sparse overrides stay until Reset. No theme-sync in v1.

Stale ChartTheme Wozduh tokens: leave unused; do not revive.


N. COLOR FORMAT
---------------

Factory mix: CSS names (blue, aqua, maroon, …) and one hex (#f23645)
and rgba fills.

Override storage: #RRGGBB (stable, picker-native).

Apply:
  lines → applyOptions({ color: "#RRGGBB" })
  channel strokes → same hex
  fill → rgba(r,g,b, factoryAlpha) where factoryAlpha is parsed from
         manifest fillColor (0.12 both channels today)

No opacity control in the UI.


O. RSX SPECIAL-PAINT BOUNDARY
-----------------------------

Owner: web/rsx-stroke-color.js + DDRFactory.withRsxStrokeColors /
updateTick per-point {time,value,color} for id line_rsx only.

Zones: value>70 green #0ebb23, value<30 red #ff0000, else MID #512DA8
(same as layout default).

This is value-driven paint on each point, not a series-level color.
User Style on line_rsx would fight per-point updates.

OUT OF V1. line_rsx_signal is a static layout color but lives on the
RSX host, not Wozduh — also out of first consumer.
